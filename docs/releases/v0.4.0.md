## Highlights

- Explicit local JSON benchmark suites with strict, immutable domain models and content fingerprints
- Versioned deterministic exact-match, normalized-match, contains, numeric-tolerance and JSON evaluators
- Sequential, bounded benchmark execution against an explicitly selected provider/model
- Atomic SQLite persistence for runs and ordered case results, separate from production metrics
- Unique-case quality aggregation with coverage, execution completeness and provenance
- Optional confidence-blended overall quality in automatic routing
- Read-only Benchmark APIs and Dashboard run, detail and quality views

## Execution and inspection

From the backend environment, deliberately invoke a local suite and target:

```bash
python -m modelpilot.benchmarks.cli run --suite ../benchmarks/suites/smoke-v1.json --provider openai --model YOUR_MODEL --max-cases 100 --timeout 30
```

This is an explicit potentially billable Provider call, not an acceptance-test command. Credentials
come from the process environment; the CLI does not load `.env` automatically. Suite/provider/model
are required, `auto` is rejected, and each case is attempted once without retry or fallback.
The max-case limit rejects oversized suites rather than truncating them. Authentication failure stops
further cases and saves produced results before exit 3. Ordinary failures/wrong answers may save with
exit 0; invalid input/configuration uses exit 2, system/persistence errors exit 4. Limits are not a
monetary budget. Temperature zero does not guarantee byte-for-byte reproducible cloud output.

HTTP exposes only GET run lists, run details and configured-suite quality. The Dashboard consumes
these read-only endpoints; it cannot execute benchmarks. Lists are bounded (default 20, max 100),
and the Dashboard calls its view recent runs, not complete history. No scheduler, background
benchmarking or automatic dataset downloads are included. See [BENCHMARKS.md](../v0.4/BENCHMARKS.md).

## Quality semantics

Quality represents performance under the pinned suite and evaluator rules, not general model ability.
A wrong evaluated answer has score 0 and is included in the weighted mean. Provider execution failure
has `evaluation=null`, contributes no quality score, and reduces completeness/confidence instead.
No evaluated cases means quality `null` and confidence 0, not a zero-quality judgment.

Aggregation strictly isolates provider/model and suite ID/version/fingerprint. Each case uses its
latest attempt by `(run.finished_at, run_id)`; a newer execution failure removes the old successful
score. Cases absent from a newer partial run may retain their most recent historical evidence.
Source run IDs and latest-run coverage/completeness expose that distinction. Repetition does not
create independent samples. The confidence rule is unchanged:

```text
clamp((unique_evaluated_cases - 5) / 45, 0, 1)
  × weighted_evaluation_coverage
  × execution_completeness
```

Category confidence uses that category's own cases. Confidence is a heuristic blending weight,
not a statistical confidence interval. A perfect three-case smoke run has quality 1 and confidence 0;
it is an integration fixture, not a model leaderboard. See [EVALUATION.md](../v0.4/EVALUATION.md).

## Routing and configuration

`MODELPILOT_QUALITY_SUITE_PATH` is opt-in and blank by default. An explicit local suite is loaded once
at startup; changing it requires a restart. Invalid paths/definitions fail startup. Enabling quality
never executes a benchmark. The Router consumes compatible overall quality using:

```text
static_quality × (1 - confidence) + benchmark_quality × confidence
```

Missing evidence, null quality, confidence zero or runtime evidence-source failure keeps static
quality; runtime failures produce sanitized warnings without failing inference. Coverage is not
applied again. Category evidence does not classify requests or choose category-specific routes.
Health eligibility comes first: high benchmark quality cannot bypass OPEN or change HALF_OPEN probes.
Latency, reliability, cost and final preference weighting retain their previous algorithms.

Quality reads aggregate all precisely matching historical runs on each lookup. No cache, TTL or
automatic expiry is included, so growing histories increase request work. Old evidence remains
traceable through source runs/timestamps and latest-run diagnostics. `generated_at` is snapshot
computation time, not a claim that evidence is fresh. QualitySnapshot is not persisted.

## Compatibility and storage

OpenAI-compatible core response fields and explicit-model behavior remain intact. Additive automatic
routing explanations include quality source, static/measured values, confidence and benchmark
provenance. Old V0.2/V0.3 explanation JSON remains readable.

SQLite schema is **4**, not 5. Fresh databases initialize at v4; v1/v2/v3 migrate through the existing
chain, preserving attempts, pricing, routing decisions and health. Benchmark run plus cases save
atomically; duplicate run IDs cannot overwrite historical records. Benchmark execution/querying does
not write production attempts, metrics, health or routing decisions. Normal chat continues recording
its own operational data.

Stop writers and take a consistent pre-upgrade backup including outstanding WAL data before opening
an older database. Schema 4 has no automatic down-migration; released v0.3.0 rejects it. Rolling back
requires a compatible pre-upgrade backup, not a schema-marker edit or a copy of the upgraded database.
Actual backup/restore commands and migration/rollback evidence are in
[COMPLETION.md](../v0.4/COMPLETION.md). Development validation uses only temporary databases.

## Limitations and deployment

No authentication, billing, streaming, LLM judge, task/category classifier, HTTP/UI benchmark
execution, distributed scheduling, new Provider, Redis or PostgreSQL is added. Bind local services
to loopback; the unauthenticated inspection API/Dashboard must not be exposed publicly by default.
Provider recovery probes are single-process only; multiple workers/instances do not share leases.
No distributed circuit-breaker guarantee is claimed.

Stored results omit raw prompts, expected answers, model output, credentials and raw Provider errors.
Local suite files intentionally contain prompts and expected answers and should not contain secrets.
No real model improvement, throughput or cost-saving claims follow from the fake-provider acceptance
tests. Release publication requires a later separately authorized push and remote CI verification.
